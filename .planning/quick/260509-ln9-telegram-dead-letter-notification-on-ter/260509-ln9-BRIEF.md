# Quick Task 260509-ln9 — Detailed Brief

**Goal:** When a `WorkflowRun` is marked FAILED via `workflow_runner.on_step_failed`, send a Telegram apology to the originating user (if a `reply_context` is available) so failures don't go silent.

## Background (why)

When a step fails, `workflow_runner.on_step_failed` (`src/robotina/queue/workflow_runner.py:331-383`) marks the step FAILED, cancels all PENDING steps, and marks the `WorkflowRun` itself FAILED — but produces no user-visible signal. The user just sees their request go quiet. This change closes the loop.

A complementary change just landed (commit `f801814`) that adds bounded retry on transient Ollama errors, so most automatic failures will not reach this dead-letter path. This dead-letter is for the residual cases that retry can't recover.

## Scope

Add a single hook inside `workflow_runner.on_step_failed`, after the FAILED-marking and step-cancellation block, before returning. The hook:

1. Reads `reply_context` from `WorkflowRun.shared_context`.
2. **If missing** (e.g. workflows triggered by scheduled tasks with no chat target): `logger.warning("Workflow failed without reply_context; skipping dead-letter | run_id=...")` and return.
3. **If present**: enqueue a `send-notification` job with `at_front=True` (per the project rule that notifications go to the front of the queue) carrying the apology text below.
4. **If the enqueue itself fails** (e.g. Redis blip): `logger.exception(...)` and swallow — do NOT raise; the workflow is already failing and we don't want to cascade.

### Apology text (Argentine Spanish, locked)

```
Algo falló procesando tu pedido (<workflow_type>). Disculpá las molestias.
```

`<workflow_type>` is the raw `WorkflowRun.workflow_type` string (e.g. `add-recipe`). No retry hint, no per-workflow templates — generic apology with the workflow label in parens. Argentine `disculpá` (not `disculpa`).

## Implementation guidance

- The `send-notification` task already has a Pydantic input model (`SendNotificationInput`) with `platform`, `chat_id`, `user_id`, `text` fields. Use whichever is canonical in the codebase. Look at how the `queue` agent tool (`src/robotina/agent/tools/queue.py`) and the `acknowledge-add-recipe` workflow step enqueue `send-notification` for the exact field shape and queue name.
- `reply_context` shape: extract `platform`, `chat_id`, and `user_id` from the `shared_context["reply_context"]` dict. Validate it has those fields; if not, treat as missing (case 2 above).
- Use `at_front=True` on the RQ enqueue — per the standing project rule, all `send-notification` jobs go to the front so user-facing replies are not blocked by long workflows.
- Keep the dead-letter helper either inline in `on_step_failed` or as a small private function in `workflow_runner.py`. Do NOT factor it out into a separate module — the user's standing preference is to avoid premature abstraction.

## Verification

1. Unit-style test: instantiate a `WorkflowRun` with `shared_context={"reply_context": {...}}`, call `on_step_failed`, assert that exactly one `send-notification` job was enqueued with `at_front=True` and the expected message body. (Use the project's existing test patterns — run via `uv run pytest`.)
2. Negative test: same but with `shared_context={}` (no `reply_context`). Assert NO `send-notification` job was enqueued and a WARN was logged.
3. (Optional, if straightforward) End-to-end via the dev environment: trigger a known-failure workflow, observe the apology landing in Telegram. If running this requires user action, skip and note in SUMMARY.

## Out of scope

- Do NOT add admin/dev-channel notifications for the no-reply_context case. Just log and skip.
- Do NOT add RQ-level step retry. Separate decision; not part of this task.
- Do NOT change `jobs.py`'s `except Exception` handler. The dead-letter is purely additive in `on_step_failed`.
- Do NOT touch the LLM backends or any agent prompts.
