## Summary

Phase 17 is **structural plumbing** — three additive code changes (one model file, one runner function, one tool class, one task-runner branch) plus one Alembic revision plus one Pydantic stub model plus REQUIREMENTS.md wording update. Every implementation choice is locked by CONTEXT.md D-01..D-08. No new patterns, no library research needed — the entire phase is a faithful application of patterns Phase 16 established for `household_id`.

The non-obvious work is **enforcing the contract at every layer**:
1. Schema: `conversation_id` NOT NULL FK + `outcome` JSON nullable (one Alembic revision)
2. Engine: `queue_workflow` gains required `conversation_id: str` arg (no default)
3. Tool: `StartWorkflowTool` gains required constructor-injected `conversation_id`
4. Runner: `run_task` `handle-incoming-message` branch resolves Conversation via `session.query(...).filter_by(...).one()` and threads `conversation.id` into the tool

**Primary recommendation:** Mirror the Phase 16 `household_id` four-layer topology exactly, MINUS the Pydantic alias layer (per Claude's Discretion in CONTEXT.md — `conversation_id` is not LLM-supplied). One single-revision Alembic file. One `NonEmptyHouseholdId` reference added (in `WorkflowOutcome` import block; the constraint alias for `conversation_id` is intentionally skipped).

### Pattern 1: Constructor-injected identity field on `BaseTool`

**What:** Identity values (`household_id`, `conversation_id`) are Pydantic-validated fields on the tool class itself, set by the caller (`run_task`) at construction, never declared in `args_schema`. The LLM cannot see, supply, or shadow them.

**When to use:** Any identity/auth/routing token that must survive across the LLM tool call but must NEVER originate from the LLM.

**Example (from current code, `src/robotina/agent/tools/start_workflow.py:122-130`):**
```python
class StartWorkflowTool(BaseTool):
    name: str = "start-workflow"
    # ... description, args_schema, return_direct ...

    # Injected by run_task() at construction time
    chat_id: str = ""
    user_id: str = ""
    platform: str = ""
    household_id: NonEmptyHouseholdId   # no default — caller MUST pass non-empty
    # Phase 17 ADD:
    conversation_id: str                 # no default — caller MUST pass
```

The `args_schema = StartWorkflowArgs` defines what the LLM may supply (`workflow_type`, `recipe_query` only). Constructor fields are separate.

### Pattern 2: Single migration file mirroring `0005_dashboard_columns.py`

**What:** One Alembic revision file, `op.add_column(...)` × N, no JSON-path SQL, no branch labels.

**Example (template from `migrations/versions/0005_dashboard_columns.py:1-33`):**
```python
"""workflow_runs: add conversation_id (FK, NOT NULL) and outcome (JSON, nullable)

Phase 17 / ARCH-01: closes the Conversation FK loop on WorkflowRun. The
table is pre-cleaned per the deploy runbook (D-08); migration is a
single revision with no backfill.

Revision ID: 0006
Revises: 0005
Create Date: 2026-05-18
"""
import sqlalchemy as sa
from alembic import op

revision = '0006'
down_revision = '0005'
branch_labels = None
depends_on = None


def upgrade() -> None:
    op.add_column(
        'workflow_runs',
        sa.Column(
            'conversation_id',
            sa.String(),
            sa.ForeignKey('conversations.id'),
            nullable=False,                   # D-01: NOT NULL upfront
        ),
    )
    op.add_column(
        'workflow_runs',
        sa.Column('outcome', sa.JSON(), nullable=True),
    )


def downgrade() -> None:
    op.drop_column('workflow_runs', 'outcome')
    op.drop_column('workflow_runs', 'conversation_id')
```

**Note on FK syntax:** Existing `migrations/versions/0002_models.py:67` uses `sa.ForeignKeyConstraint(['conversation_id'], ['conversations.id'])` inside `op.create_table()`. Since we're using `op.add_column`, the inline `sa.ForeignKey(...)` form inside the column definition is the established Alembic pattern for adding-FK-with-column. (If the planner prefers, `op.create_foreign_key(...)` as a follow-up step is also valid; the inline form is simpler.)

### Pattern 3: `.one()` for invariant lookups

**What:** `session.query(Conversation).filter_by(platform=..., chat_id=...).one()` — raises `sqlalchemy.exc.NoResultFound` on miss, `MultipleResultsFound` on duplicate. Both are invariant violations (Conversation has `UniqueConstraint("platform", "chat_id")` per `src/robotina/gateway/models.py:28`).

**When to use:** Any read where the absence of the row is a bug, not a normal case.

**Already-established sites:** `gateway/handler.py:56-58` and `gateway/handler.py:70-72` already use `.filter_by(platform=Platform.TELEGRAM, chat_id=chat_id).first()` (the `.first()` variant tolerates NULL because gateway is the upsert site). The `run_task` lookup (D-04) is downstream of that upsert and uses `.one()` because the row is guaranteed present.

### Anti-Patterns to Avoid

- **JSON-path SQL in the migration body** (e.g., `op.execute("UPDATE workflow_runs SET conversation_id = (SELECT id FROM conversations WHERE chat_id = shared_context->'reply_context'->>'chat_id')")`). Per D-02, the migration is `add_column` × 2 only. JSON-glue migrations are exactly the trap PITFALLS Pitfall 3 warns about; the D-08 runbook sidesteps it via pre-clean.
- **Pydantic alias for `conversation_id`** (e.g., `NonEmptyConversationId = Annotated[str, Field(min_length=1, ...)]`). Recommended skip per Claude's Discretion in CONTEXT.md — `conversation_id` is system-generated, not LLM-supplied, so the LLM-shadowing motivation for `NonEmptyHouseholdId` doesn't apply. FK NOT NULL + `.one()` raise = sufficient.
- **Parallel guard for empty `conversation_id` in `queue_workflow`.** The Phase 16 `household_id` REQ-HID-4 guard (workflow_runner.py:138-144) defends against LLM-supplied empties; per CONTEXT.md "Established Patterns," Phase 17 does NOT add a parallel guard for `conversation_id` — FK NOT NULL + `.one()` raise cover it.
- **Stripping `shared_context["reply_context"]` writes from `StartWorkflowTool._run`** (lines 144-152). Per ARCH-05, the deprecation window is open through v1.1. Keep the writes. Workflow steps (`agent/workflows.py:105-159`) still read `reply_context` from `shared_context`; the dead-letter block (`workflow_runner.py:495-503`) also reads it.
- **Lookup inside `StartWorkflowTool._run`** (instead of `run_task`). Rejected by D-04 — Phase 18 will need the same lookup site for `RobotinaInvocation`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Defensive `conversation_id is None` checks scattered in `queue_workflow` | `if not conversation_id: raise ValueError(...)` | FK NOT NULL constraint + `.one()` raise + type-hinted signature (`conversation_id: str` with no default) | Three independent layers (DB constraint, ORM lookup that raises, Python type system) cover the invariant. A parallel Python-level guard is dead code. |
| Backfill UPDATE statements in the migration | `op.execute("UPDATE ... SET conversation_id = (SELECT ...)")` | Operator pre-clean (D-08 TRUNCATE) | Per D-02. JSON-path SQL in migrations is the exact trap PITFALLS Pitfall 3 documents. |
| Custom `NonEmptyConversationId` Annotated alias | `Annotated[str, Field(min_length=1, pattern=r"^\S(.*\S)?$")]` | Bare `str` type on `StartWorkflowTool.conversation_id`; FK + `.one()` carry the invariant | LLM cannot supply this field (it's not in `args_schema`). Pydantic field validation here would defend against zero attackers. (Phase 16 alias defended against LLM-supplied identity fields, which IS a real attack surface — this is not.) |
| Migration pre-flight check (`SELECT COUNT(*) FROM workflow_runs WHERE conversation_id IS NULL`) | An `op.execute(...)` SELECT in `upgrade()` | Operator follows D-08 runbook; Alembic/Postgres fail loudly on non-empty table | Per D-02 ("If the table is non-empty when the migration runs, Alembic / Postgres will fail loudly on the NOT NULL constraint — that is the intended signal"). |

**Key insight:** This phase is **subtractive** in defensive-coding terms — every "should we add a guard?" question is answered "no, the schema/DB enforces it." The Phase 16 four-layer pattern was correct for `household_id` (LLM-supplied) but is overkill for `conversation_id` (system-generated UUID).

## Common Pitfalls

### Pitfall 1: Forgetting to update workflow_runner integration tests that construct `queue_workflow(...)` without `conversation_id`

**What goes wrong:** `tests/test_workflow_runner.py` contains 4+ test cases that call `queue_workflow(workflow_type=..., shared_context=..., household_id=..., queue=..., session=...)` without `conversation_id`. After D-05 makes `conversation_id` required (no default), these tests fail at Python-signature level — TypeError missing positional arg — not the assertion they were written to verify.

**Why it happens:** The required-arg signature change ripples through every call site in tests. Pytest's collection phase will surface them, but planner must enumerate them explicitly so Wave 0 RED-state is intentional, not collateral damage.

**How to avoid:**
- Wave 0: ADD test stubs that assert `queue_workflow` raises on missing `conversation_id` and that `WorkflowRun.conversation_id` is non-null on success.
- Wave 1: Update ALL existing `queue_workflow(...)` call sites in `tests/test_workflow_runner.py` to pass `conversation_id="test-conv-id"` (or a real Conversation row id in integration tests).
- **Sites to update (verified in `tests/test_workflow_runner.py`):**
  - `test_step_input_persisted_on_first_enqueue` (line ~619-679) — uses `queue_workflow` directly with a mocked session; needs `conversation_id="conv-1"` added
  - `test_queue_workflow_rejects_empty_household_id` (line ~799-823) — needs `conversation_id="conv-1"` added (test focuses on household_id; conversation_id must be valid)
  - `test_queue_workflow_rejects_whitespace_household_id` (line ~826-847) — same as above

**Warning signs:** `TypeError: queue_workflow() missing 1 required positional argument: 'conversation_id'` on test collection.

### Pitfall 2: `StartWorkflowTool` construction in `run_task` missing `conversation_id`

**What goes wrong:** `src/robotina/queue/jobs.py:144-149` currently constructs `StartWorkflowTool(chat_id=..., user_id=..., platform=..., household_id=...)`. After D-03, `conversation_id` is required (no default per the Phase 16 `household_id` precedent). Forgetting to pass it = ValidationError at agent setup time, before the LLM is invoked = the entire handle-incoming-message branch crashes for every Telegram message.

**Why it happens:** The `run_task` change is two edits at the same call site: (a) compute `conversation = session.query(...).one()`, and (b) pass `conversation_id=conversation.id` into the constructor. Easy to do (a) without (b).

**How to avoid:**
- Test (`tests/unit/test_agent_runner.py::test_run_task_injects_all_three_tools_for_handle_incoming_message`, line ~271-349) currently asserts `sw_tools[0].household_id == "household-abc"`. ADD an assertion `sw_tools[0].conversation_id == "<expected conv id from mocked session>"`.
- Test must mock `session.query(Conversation).filter_by(...).one()` to return a Conversation with a known id.

**Warning signs:** Pydantic `ValidationError: 1 validation error for StartWorkflowTool: conversation_id Field required` in worker logs.

### Pitfall 3: `tests/unit/test_start_workflow_tool.py` constructs the tool without `conversation_id`

**What goes wrong:** Every test in `tests/unit/test_start_workflow_tool.py` constructs `StartWorkflowTool(chat_id="c1", user_id="u1", platform="telegram", household_id="h1")` (e.g., lines 18-20, 28-30, 56-58, 83-85, 127-129, 176-178, 202-204, 222-224, 255-257, 271-273, 285-287, 294-296, 315-317, 343-345). Adding the required `conversation_id` field means **every one of these constructor calls breaks**.

**Why it happens:** Phase 16 set the same trap; this is the same shape repeated.

**How to avoid:**
- Wave 0: ADD `test_constructor_rejects_missing_conversation_id` and `test_constructor_accepts_non_empty_conversation_id` (mirror existing `test_constructor_requires_household_id_no_default` at line 278-287).
- Wave 1: BULK update every existing `StartWorkflowTool(...)` constructor call in `test_start_workflow_tool.py` to add `conversation_id="conv-1"` (the planner should list these explicitly — there are ~15 sites).
- ALSO: assert `tool.conversation_id == "conv-1"` lives somewhere (sanity for the new field).

**Warning signs:** ~15 Pydantic ValidationErrors at test collection.

### Pitfall 4: `_set_household_id` conftest fixture does NOT cover `conversation_id` — but it doesn't need to

**What goes wrong:** `tests/conftest.py:14-22` autouse-injects `HOUSEHOLD_ID="test-household"`. A naive read might assume Phase 17 needs an analogous `_set_conversation_id` fixture.

**Why it happens:** `HOUSEHOLD_ID` is an env var the gateway reads at every message. `conversation_id` is NOT an env var — it's a per-Conversation UUID resolved per job. The fixture analogy doesn't apply.

**How to avoid:** Don't add a `_set_conversation_id` autouse fixture. For test cases that need a Conversation row, either (a) use a mock session that returns a MagicMock Conversation, or (b) use a real db_session fixture that INSERTs a Conversation. The existing `db_session` fixture in `tests/conftest.py:26-34` is the right substrate.

### Pitfall 5: Existing `shared_context["reply_context"]` reads break

**What goes wrong:** Multiple sites STILL read `shared_context.reply_context` per ARCH-05 deprecation window:
- `workflow_runner.py:495-515` (dead-letter `send-notification` block in `on_step_failed`)
- `agent/workflows.py:105-159` (every step's `build_input`)
- `agent/tools/start_workflow.py:144-152` (continues to WRITE reply_context into shared_context — preserve this!)

A well-meaning developer cleaning up the schema could remove the `reply_context` writes in `start_workflow.py` thinking they're redundant now that `conversation_id` is the new source of truth — and silently break the dead-letter apology and all step `build_input` chains.

**Why it happens:** The deprecation window pattern is counterintuitive — the "old" path stays writable through v1.1 even though the "new" FK is now authoritative for *future* reads (Phase 18+).

**How to avoid:**
- **Phase 17 explicitly does NOT remove any `reply_context` reads or writes.** Document this prominently in PLAN.md "Do Not Touch" section.
- Add a test (or extend an existing test) that asserts `WorkflowRun.shared_context["reply_context"]` is still populated after `queue_workflow` runs through `StartWorkflowTool`.

**Warning signs:** `workflow_runner.py:495` `(run.shared_context or {}).get("reply_context")` returning `None` on a freshly-failed workflow → dead-letter apology silently skipped.

### Pitfall 6: Conversation row not yet committed when `run_task` looks it up

**What goes wrong:** `gateway/handler.py:54-110` upserts Conversation, then `session.commit()` at line 110. Only AFTER that commit does it enqueue the job (line 125-132). So in production, by the time `run_task` runs, the Conversation row IS visible. But test scenarios that mock the gateway path and directly enqueue a job (bypassing the gateway commit) can hit a `NoResultFound` because no Conversation exists in the test DB.

**Why it happens:** The transactional ordering (gateway commits, THEN enqueues) is the invariant `.one()` relies on. Tests that don't replicate it will fail-loud — which IS the desired contract.

**How to avoid:**
- For integration tests on `run_task`: pre-insert a Conversation via `db_session` fixture BEFORE enqueueing.
- For unit tests on `run_task`: mock `session.query(Conversation).filter_by(...).one()` to return a MagicMock.

**Warning signs:** `sqlalchemy.exc.NoResultFound: No row was found when one was required` in a test that doesn't pre-insert a Conversation.

### Pitfall 7: `Platform(task_input.platform)` raises ValueError on unknown platform string

**What goes wrong:** `Platform` is an `enum.Enum` with only `TELEGRAM = "telegram"`. The lookup in D-04 uses `Platform(task_input.platform)` to coerce the string to the enum value. If `task_input.platform` is anything other than `"telegram"`, this raises `ValueError: 'X' is not a valid Platform` BEFORE the `.one()` call, surfacing as an opaque failure inside `run_task`.

**Why it happens:** `IncomingMessageInput.platform: Literal["telegram"]` (task_types.py:144) constrains the input model — so this can only fail if the model was constructed by a non-Pydantic path. Defensive but unlikely.

**How to avoid:** Trust the Pydantic input model contract. If `IncomingMessageInput` was constructed, `platform == "telegram"` is guaranteed. No additional guard needed.

**Warning signs:** `ValueError: 'something' is not a valid Platform` in `run_task` — would indicate `IncomingMessageInput` constraint was bypassed.

1. **Should `WorkflowOutcome` (D-07) live next to `NonEmptyHouseholdId` (early in `task_types.py`, near the constraint aliases) or as a new section near the end?**

   - What we know: Both work in Alembic. `0002_models.py:67-93` uses inline FK syntax via `sa.ForeignKeyConstraint` inside `op.create_table()`. There is no existing `op.add_column + FK` precedent in the migrations dir.
