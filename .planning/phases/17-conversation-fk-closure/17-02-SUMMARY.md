## Decisions Made

- **Inline `sa.ForeignKey('conversations.id')` positional arg style** (not `op.create_foreign_key`). Mirrors the unnamed-FK convention used in `0001_init.py` through `0005_dashboard_columns.py`. Postgres autonames as `workflow_runs_conversation_id_fkey`. The alternative (`op.create_foreign_key` with explicit name) would have required a constraint-name argument that no prior migration declares.
- **WorkflowOutcome placed at file END, not next to `NonEmptyHouseholdId`.** Per D-07, the stub is a Phase 20 anchor, not an active model used by current task inputs. Keeping it separate (with a banner-comment header) signals "future-phase fill-in" rather than "active model"; Phase 20 will extend in-place without touching the existing block of Phase 15 Recipe* models.
- **No `NonEmptyConversationId` alias** (D-03 explicit). `conversation_id` is system-generated by Wave 2's `session.query(Conversation).filter_by(...).one()` — there is no LLM-shadowing attack surface that would justify a Pydantic-level guard. FK + raise are sufficient.
- **No `relationship(...)` to `Conversation` from `WorkflowRun`.** Out of scope this phase (Phase 17 WRITES the FK; Phase 18+ READS it). Adding a relationship now would expand the import surface (would need to import `Conversation` from `gateway.models`, creating queue->gateway dependency that doesn't exist today) without any caller using it.
