Dockerfile skeleton (minimal, no multi-stage build — Phase 13 is dev+staging only, image size optimization is out of scope):
```dockerfile
# Phase 13 / DASH-09: dashboard deployment image.
# Multi-purpose: any `uv run <script>` from pyproject.toml [project.scripts]
# can be the CMD. Default is `uv run dashboard`.
FROM python:3.12-slim

# Install uv (pinned to a known-good version).
RUN pip install --no-cache-dir 'uv>=0.4'

WORKDIR /app

# Copy pyproject + lockfile first to maximize Docker layer caching.
COPY pyproject.toml uv.lock ./

# Copy source + migrations needed at runtime.
COPY src ./src
COPY migrations ./migrations
COPY alembic.ini ./

# Install the project itself (editable install picks up the [project.scripts]
# entry points, so `uv run dashboard` resolves to robotina.dashboard:main).
RUN uv sync --no-dev --frozen

# Dashboard default; override CMD for other entrypoints (gateway, agent, all).
EXPOSE 8001
CMD ["uv", "run", "dashboard"]
```

Note: `uv.lock` is required at the same path as `pyproject.toml` for `uv sync --frozen` to work. If `uv.lock` does not exist at repo root, drop `--frozen` and accept that the image build will re-resolve dependencies (slower but correct). Check `ls uv.lock` before adopting the Dockerfile and choose the correct flag.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Compose network → host port 8001 | The dashboard publishes `8001:8001`, exposing the dashboard on localhost on the developer/staging machine. Anyone with network access to that host can reach the dashboard without auth. |
| Container → Postgres | DATABASE_URL is set to the in-network postgres service; no external DB access. |
| Image build context | `build: .` copies the repo root into the image. The Dockerfile uses an allow-list of paths (`COPY src`, `COPY migrations`, `COPY alembic.ini`, `COPY pyproject.toml uv.lock`) — NOT `COPY . .` — so `.env`, secrets, `node_modules`, `.git`, etc. do not enter the image. |
| `.env.example` documentation | Documents `DASHBOARD_PORT` as a non-secret env var. No secrets are introduced by this plan. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-13-07 | Information disclosure | Dashboard accessible on `0.0.0.0:8001` of the host without auth | accept (deployment context) | This plan publishes `8001:8001` which binds to all host interfaces. In dev that means localhost; in staging that means the staging-VM's primary interface. The deployment-context assumption (SPEC §"Out of scope": auth deferred until exposed beyond compose network) is documented. If staging is exposed publicly, a future phase adds auth. For the current dev+staging scope, this is accepted. |
| T-13-08 | Tampering | Dockerfile copies arbitrary repo content into the image | mitigate | Explicit `COPY src ./src`, `COPY migrations ./migrations`, `COPY alembic.ini ./`, `COPY pyproject.toml uv.lock ./`. No `COPY . .`. Secrets in `.env` / credentials directories do not enter the image. Reviewable in the Dockerfile diff. |
| T-13-09 | Denial of service | Unauthenticated dashboard polled by external traffic | accept (deployment context) | Same accept rationale as T-13-07. The polling cadence is 3s/10s; even a malicious bot at full speed against this surface would saturate Postgres, not the dashboard. Polling halt + 50-row LIMIT cap the per-request cost. |
| T-13-10 | Tampering | `.env` accidentally copied into image | mitigate | The Dockerfile uses explicit COPY paths (allow-list). `.env` is NOT in the list. A `.dockerignore` file would be a belt-and-suspenders mitigation; out of scope for this plan unless `.env` actually ends up in the image (verify with `docker run --rm dashboard ls -la /app/.env || echo absent`). |
| T-13-11 | Repudiation | Manual smoke checkpoint pass/fail not recorded | mitigate | The checkpoint resume-signal goes into the plan's SUMMARY.md per `<output>` block — the human's pass/fail observation becomes part of the persistent record. |

Severity assessment: All threats are MEDIUM or below. T-13-07 / T-13-09 are accepted because the deployment context (dev+staging, no public exposure) is the SPEC-locked scope; auth is explicitly deferred. Plan proceeds.
