# Phase 13 — UI Design Contract

> Visual and interaction contract for the Queue Visibility Dashboard. Server-rendered FastAPI + Jinja2 + HTMX. Dev + staging only. Read-only debugger surface. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Visual Identity & Tone

| Property | Value |
|----------|-------|
| Audience | One developer debugging a failed Robotina workflow on a laptop |
| Tone | Utilitarian, terse, technical, English-only |
| Anti-tone | NOT consumer, NOT marketing, NOT delightful, NOT animated beyond one functional pulse |
| Density | High — assume the developer wants 50 runs visible without scrolling on a 1440-tall display |
| Inspiration | `rq-dashboard`, `htop`, `pgAdmin` — terminal-adjacent, no decoration |
| Brand chrome | One line of header text: `Robotina Queue Dashboard` + current page name. No logo, no avatar, no nav menu beyond the project-name link back to `/` |

## Layout & Responsive Breakpoints

**Desktop-first.** Developers use this on laptops; mobile is secondary but must not break.

| Breakpoint | Width | Behavior |
|------------|-------|----------|
| Default (desktop) | ≥1024px | Page content centered in `max-width: 1200px` container with `padding: 0 24px`. List view: single table fills container width. Detail view: two stacked sections — workflow header card on top, step-list below. Step rows display step header (key, status, timestamps) on one line; `step_input` and `artifact` JSON panels stacked vertically below the header inside the step row |
| Narrow desktop | 640–1023px | Same as desktop but `padding: 0 16px`; step JSON panels remain stacked |
| Mobile | <640px | Container becomes full-width with `padding: 0 12px`. List view: table cells wrap; `created_at` column hides below 480px (kept in `title` attribute on the row link for hover/tap). Detail view: step header items wrap to multiple lines. JSON panels remain readable with `overflow-x: auto` |

**Layout primitives:**
- Outer wrapper `<div class="container">` with `max-width: 1200px`, centered, horizontal padding from token table above
- `<header class="page-header">` is full-width, sits above container, height 48px, single-line, no nav
- `<main>` holds the routed view content
- No sidebar. No footer.
- No fixed/sticky elements except the page header (`position: sticky; top: 0; z-index: 1`)

**Visual rhythm:**
- Vertical spacing between top-level sections: 24px (`--space-lg`)
- Vertical spacing between step rows: 8px (`--space-sm`)
- Step row internal padding: 16px (`--space-md`)
- Workflow header card padding: 24px (`--space-lg`)

## Spacing Scale

Declared values (multiples of 4):

| Token | CSS variable | Value | Usage |
|-------|--------------|-------|-------|
| xs | `--space-xs` | 4px | Badge internal padding (vertical), inline icon gaps |
| sm | `--space-sm` | 8px | Badge internal padding (horizontal), gap between adjacent step rows, gap between status badge and adjacent text |
| md | `--space-md` | 16px | Step row internal padding, gap between fields inside a step header line, table cell padding |
| lg | `--space-lg` | 24px | Workflow header card padding, vertical gap between top-level page sections, container horizontal padding (desktop) |
| xl | `--space-xl` | 32px | Vertical space below page header before content begins |
| 2xl | `--space-2xl` | 48px | Page header height; empty-state vertical padding |

Exceptions: none. Every CSS rule that sets `padding`, `margin`, `gap`, or `top/bottom/left/right` must reference one of the six tokens above.

## Typography

Three sizes, two weights. System fonts only.

| Role | CSS variable | Size | Weight | Line Height | Usage |
|------|--------------|------|--------|-------------|-------|
| Body | `--font-body` | 14px | 400 | 1.5 | Default UI text, table cells, step headers |
| Mono | `--font-mono` | 13px | 400 | 1.5 | JSON blocks, workflow IDs, RQ job IDs, timestamps |
| Heading | `--font-heading` | 18px | 600 | 1.3 | Page section headers ("Workflow #abc123", "Steps") |
| Label | `--font-label` | 12px | 600 | 1.2 | Badge text (uppercase tracked), table column headers (uppercase tracked) |

Letter-spacing: badges and table headers use `letter-spacing: 0.04em` + `text-transform: uppercase`. Everything else inherits the default 0.

No display size, no oversized hero text — this is a tool, not a landing page.

## Color

Cool-gray neutral surface with semantic accent colors only on status badges. Light theme only (dark theme out of scope — explicit deferral).

| Role | CSS variable | Hex | Usage |
|------|--------------|-----|-------|
| Dominant (60%) | `--color-bg` | `#FAFAFA` | Page background |
| Secondary (30%) | `--color-surface` | `#FFFFFF` | Step rows, workflow header card, table rows |
| Secondary alt | `--color-surface-alt` | `#F4F4F5` | Page header bar, table column header row, JSON panel background |
| Border | `--color-border` | `#E4E4E7` | Card borders, table cell borders, JSON panel border |
| Text primary | `--color-text` | `#18181B` | Body text, headings |
| Text muted | `--color-text-muted` | `#71717A` | Timestamps, metadata labels, "no steps yet" placeholders |
| Accent (10%) | `--color-accent` | `#2563EB` | RESERVED — see list below |
| Destructive | not used | — | No destructive actions in this phase (read-only) |

**Accent (`#2563EB`) is reserved for:**
1. Hyperlinks (workflow ID in list rows linking to detail view; "back to list" link in detail view)
2. `RUNNING` status badge fill color
3. Keyboard focus outlines (`:focus-visible { outline: 2px solid var(--color-accent); outline-offset: 2px; }`)

Accent is NEVER used for: buttons (none exist), backgrounds, borders of non-running rows, hover states on non-link elements.

### Status Badge Color Tokens

Five status states. `FAILED` and `CANCELLED` MUST be visually distinguishable via more than just color (pairing with stripe-pattern texture and text label — see Accessibility section).

| Status | CSS class | Background | Border | Text | Texture | Animation |
|--------|-----------|------------|--------|------|---------|-----------|
| `PENDING` | `badge badge--pending` | `transparent` | `1px solid #D4D4D8` | `#52525B` | none | none |
| `RUNNING` | `badge badge--running` | `#2563EB` (var `--color-accent`) | `1px solid #2563EB` | `#FFFFFF` | none | `subtle-pulse 2s ease-in-out infinite` (opacity 1.0 ↔ 0.7); `@media (prefers-reduced-motion: reduce)` disables it |
| `DONE` | `badge badge--done` | `#16A34A` | `1px solid #16A34A` | `#FFFFFF` | none | none |
| `FAILED` | `badge badge--failed` | `#DC2626` | `1px solid #DC2626` | `#FFFFFF` | solid fill — strongest visual weight on the page | none |
| `CANCELLED` | `badge badge--cancelled` | diagonal-stripe `repeating-linear-gradient(45deg, #FEF3C7 0 6px, #FDE68A 6px 12px)` | `1px solid #F59E0B` | `#92400E` | diagonal stripes are the FAILED-vs-CANCELLED grep-able differentiator | none |

**The grep-able FAILED-vs-CANCELLED differentiator in rendered HTML:**
- `class="badge badge--failed"` for FAILED — solid red, white text
- `class="badge badge--cancelled"` for CANCELLED — striped amber/orange — CSS background uses `repeating-linear-gradient` which is a unique selector against the FAILED rule
- Acceptance test `grep 'badge--failed' rendered.html` AND `grep 'badge--cancelled' rendered.html` both succeed on a failed-cascade workflow detail view, and the two class strings are distinct

### Color Contrast (WCAG)

All foreground/background pairs above meet WCAG AA contrast (≥4.5:1 for body, ≥3:1 for large text and UI components):

| Pair | Ratio | Standard |
|------|-------|----------|
| `--color-text` on `--color-bg` (#18181B on #FAFAFA) | 16.1:1 | AAA |
| `--color-text-muted` on `--color-bg` (#71717A on #FAFAFA) | 4.6:1 | AA body |
| White on `#2563EB` (RUNNING) | 4.7:1 | AA |
| White on `#16A34A` (DONE) | 4.6:1 | AA |
| White on `#DC2626` (FAILED) | 4.8:1 | AA |
| `#92400E` on `#FDE68A` (CANCELLED) | 4.6:1 | AA |
| `#52525B` on `#FAFAFA` (PENDING) | 7.9:1 | AAA |
| `--color-accent` link on `--color-bg` (#2563EB on #FAFAFA) | 5.0:1 | AA |

## Component Contracts

Eight components, each rendered by a Jinja2 macro or template fragment.

### 1. Page Header (`base.html`)
- Sticky single-line bar, full viewport width, height 48px (= `--space-2xl`)
- Background `--color-surface-alt`, bottom border `1px solid --color-border`
- Left: anchor `<a href="/">Robotina Queue Dashboard</a>` — accent-colored, label typography
- Right: empty (reserved; do not add controls)

### 2. List View Workflow Row (`_run_rows.html`)
Rendered as `<tr>` inside a `<table class="runs">`.
- Columns in order: ID (mono, 8-char short id, clickable link to detail), TYPE (body text), HOUSEHOLD (body text, muted if empty), STATUS (`_status_badge.html` macro), CREATED (mono, ISO-8601 `YYYY-MM-DD HH:MM:SS` in UTC)
- Row height: `--space-2xl` (48px), padding `--space-md` horizontal on each `<td>`
- Hover: row background `--color-surface-alt`; the entire row is clickable via the ID link being the `<tr>`'s first child anchor
- Border-bottom: `1px solid --color-border` between rows; top row also has border-top; container border-radius 4px on the wrapping `<table>` is fine if implemented via wrapper div

### 3. Status Badge (`_status_badge.html` macro)
- Signature: `{{ status_badge(status) }}` — takes one of `PENDING | RUNNING | DONE | FAILED | CANCELLED`
- Renders: `<span class="badge badge--{{ status|lower }}">{{ status }}</span>`
- Visual spec defined in Color section above
- Display: `inline-flex`, padding `--space-xs --space-sm` (4px 8px), border-radius 4px, font-size 12px, weight 600, uppercase, letter-spacing 0.04em
- Accessibility: text label is always rendered alongside (or as) the visual — never icon-only

### 4. Workflow Header Card (top of `workflow.html`)
- `<section class="workflow-header">` with `--color-surface` background, `1px solid --color-border`, padding `--space-lg`, border-radius 4px
- Contents (top to bottom):
  - `<h1>Workflow {short_id}</h1>` heading typography
  - Subhead muted line: `{workflow_type} · household {household_id}`
  - Status badge (large or normal-size)
  - Two-column key/value grid for: `Created`, `Started` (if any), `Completed` (if any), full UUID (mono)
  - Optional `Shared context` section: collapsible `<details>` element containing `<pre class="json-block">` with shared_context JSON

### 5. Step Row Card (inside `_workflow_body.html`)
- `<article class="step-row" data-status="{{ step.status }}">`
- Background `--color-surface`, border `1px solid --color-border`, border-radius 4px, padding `--space-md`, gap-below `--space-sm`
- Internal layout (top to bottom):
  - Header line (flex row, gap `--space-md`): `<span class="step-key">{{ step.step_key }}</span>`, status badge, `Started: {{ ts }}`, `Completed: {{ ts }}` (muted, mono, hidden if null)
  - When status is `FAILED`: `<div class="failure-block">Failure: <code>{{ step.failure_reason }}</code></div>` — accent-colored left border `4px solid #DC2626`, padding-left `--space-md`
  - `Input` label + `<pre class="json-block">{{ step.step_input | tojson(indent=2) }}</pre>`
  - `Output` label + `<pre class="json-block">{{ step.artifact | tojson(indent=2) }}</pre>` — shown only if `step.artifact is not none`; otherwise the entire Output section is omitted (NOT shown as "(none)" — reduce noise)

### 6. JSON Block (`<pre class="json-block">`)
- Background `--color-surface-alt`, border `1px solid --color-border`, padding `--space-md`, border-radius 4px, font-mono 13px, line-height 1.5
- `overflow-x: auto` to handle long lines without breaking layout
- `white-space: pre` (preserves indentation)
- `max-height: 400px; overflow-y: auto` (large artifacts don't dominate the viewport)
- No syntax highlighting — keep zero JS deps

### 7. Polling Wrapper Element
The grep-able interaction contract for HTMX polling halt.

- **List view wrapper** (always polls):
  `<tbody id="runs-body" hx-get="/fragments/runs" hx-trigger="every 10s" hx-swap="outerHTML">…rows…</tbody>`
- **Detail view wrapper — non-terminal** (polls):
  `<div id="workflow-body" hx-get="/fragments/workflows/{{ run.id }}" hx-trigger="every 3s" hx-swap="outerHTML">…body…</div>`
- **Detail view wrapper — terminal (DONE / FAILED)** (polling halts):
  `<div id="workflow-body">…body…</div>`
  Note: the `hx-trigger` attribute is ABSENT. This is the load-bearing markup difference. Acceptance test asserts `'hx-trigger' not in response_text` when the workflow is in a terminal status.

### 8. Empty State (`empty-state` block)
- Centered, `--space-2xl` vertical padding
- `<h2>` (`No workflows yet`) in heading typography, muted color
- `<p>` body text with the "Start a workflow…" prompt
- No illustration, no icon

## Interaction Contracts

| Interaction | Contract |
|-------------|----------|
| Click workflow ID in list row | Navigate (`<a href="/workflows/{id}">`) to detail view. Standard HTML link — no HTMX, no JS interception |
| Click "← All workflows" on detail view | Navigate (`<a href="/">`) to list view |
| List view auto-refresh | HTMX `hx-trigger="every 10s"` on `<tbody id="runs-body">`. Cadence is unconditional — list always polls regardless of any workflow's status |
| Detail view auto-refresh | HTMX `hx-trigger="every 3s"` on `<div id="workflow-body">` when the visible workflow's status is `PENDING` or `RUNNING`. When status is `DONE` or `FAILED`, the server-rendered wrapper omits the `hx-trigger` attribute; HTMX swaps in the trigger-less wrapper; polling halts naturally |
| Hover on list row | Background changes to `--color-surface-alt`. No tooltips, no popovers |
| Hover on JSON block | No change. Block stays static |
| Keyboard navigation | All links reachable via Tab. Focus ring uses `--color-accent` with 2px outline, 2px offset. No custom keyboard shortcuts |
| Mobile tap | Same affordances as desktop. Row hover state activates on `:active` |
| Out of scope: client-side filter / search / sort / pagination | None implemented this phase. No search input, no column-header sort, no page numbers. The 50-row hard cap is enforced server-side |
| Out of scope: mutating actions | No retry button, no cancel button, no requeue. Read-only |
| Out of scope: WebSocket / SSE | Polling only |

## State Definitions

For every component, define what's shown in each state.

### List View states
- **Loading (initial render):** Server-rendered HTML returns synchronously. There is no skeleton/spinner; the page either renders rows or the empty state on first byte
- **Empty (0 workflow runs):** Empty-state block with heading and body copy (see Copywriting). No `<table>` rendered
- **Populated:** `<table>` with up to 50 rows, newest first. Each row is a workflow run
- **HTMX polling re-render:** The `<tbody id="runs-body">` element swaps. Header `<thead>` does NOT swap. Empty state, if reached after a polling cycle, replaces the `<table>` entirely (server returns the empty-state markup wrapped in a `<tbody>`-compatible structure or the polling endpoint returns the full page-replace markup — choose at implementation time, document in PLAN.md)
- **Error (500 on `/fragments/runs`):** HTMX default behavior; no custom handling. The dashboard logs the exception; the table is not updated. Developer reloads manually

### Detail View states
- **Loading (initial render):** Server-rendered HTML returns synchronously. No skeleton
- **Workflow not found (404):** 404 page with "Workflow not found" heading and body copy (see Copywriting). HTTP status 404
- **Workflow exists, 0 steps:** Workflow header card renders; step list section renders the "This workflow has no steps recorded." placeholder. Steps section heading still appears
- **Workflow exists, steps in mix of states:** Each step renders per its status; FAILED step shows failure block; CANCELLED steps have striped badges; DONE steps may show output block; RUNNING step shows pulsing badge
- **Terminal workflow:** Wrapper element omits `hx-trigger` attribute. Polling halts
- **Non-terminal workflow:** Wrapper element includes `hx-trigger="every 3s"`. Polling continues
- **Error (500 on `/fragments/workflows/{id}`):** HTMX default behavior; no custom UI

### Server error states (full-page)
- **500 (template render / DB exception on full-page route):** FastAPI exception handler returns a minimal HTML page with "Dashboard error" heading and the formatted exception message. Header bar still renders so the developer can navigate back to `/`

## Accessibility

Minimum compliance: WCAG 2.1 AA + the project's color-contrast targets above.

- **Semantic HTML:** Use `<table>` for tabular data (list view), `<article>` for step cards, `<header>`/`<main>`/`<section>` landmarks, `<h1>`/`<h2>` heading hierarchy. No `<div soup>`
- **Color is never the sole signal:** Every status badge pairs color with the text label (`PENDING`, `RUNNING`, etc.) and, for `CANCELLED`, the diagonal-stripe pattern adds a non-color texture. A red-green-colorblind developer reading the dashboard sees: solid-filled colored badge with text "FAILED" vs. striped colored badge with text "CANCELLED" — distinguishable without hue
- **Focus visibility:** `:focus-visible` styles use `2px solid --color-accent` outline with `2px` offset on every interactive element (links). The default browser focus ring is replaced uniformly
- **Tab order:** Reflects DOM order. No `tabindex` overrides beyond `tabindex="0"` for anything custom (none expected)
- **Reduced motion:** `@media (prefers-reduced-motion: reduce) { .badge--running { animation: none; } }` — the pulse animation respects the user preference. No other animation exists, so this is the only rule
- **Screen reader:** Status badges include their text label, so `<span class="badge badge--failed">FAILED</span>` announces as "FAILED". The striped CANCELLED pattern is decorative CSS — screen reader reads only the "CANCELLED" text. No `aria-hidden` games needed
- **Language tag:** `<html lang="en">` — English only by phase decision (no Spanish UI in this phase)
- **Page title:** Browser tab title updates per page (see Copywriting)
- **Skip-to-content link:** Out of scope — single-page-flow, no complex nav to skip. Re-evaluate if a sidebar or nav is added in a future phase

## Independence from Other Robotina Modules (D-01 enforcement at the UI layer)

Hard rule from CONTEXT.md D-01 echoed at the visual layer:

- **No design tokens shared.** The dashboard's CSS custom properties (`--color-*`, `--space-*`, `--font-*`) are declared on `:root` inside `src/robotina/dashboard/static/dashboard.css` ONLY. No other Robotina module declares CSS (the gateway, agent, and queue modules are pure Python with no UI). If a future module introduces UI, it MUST NOT import or reuse `dashboard.css` — it gets its own
- **No shared templates.** Jinja2 templates live in `src/robotina/dashboard/templates/`. No other module renders HTML. Templates do not import from outside the dashboard module
- **No shared static assets.** `htmx.min.js` is vendored inside `dashboard/static/` and not reused elsewhere. If the scheduler API ever needs HTMX, it gets its own copy
- **No shared FastAPI app object.** The dashboard's `FastAPI` instance is private to the dashboard module. Even if the scheduler API gets a FastAPI app later, the dashboard does not export its `app` for cross-module mounting
- **Grep-able enforcement:** SPEC AC `grep -rE "from robotina\.dashboard|import robotina\.dashboard" src/robotina/ --exclude-dir=dashboard` returns zero matches. This guards Python imports; the CSS/templates/static rules above are enforced by code review (no automated check needed — there is no other UI to leak into)
